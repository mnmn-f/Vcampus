# 角色与职责边界

系统采用“一个用户可拥有多个角色、登录后进入一个职责工作台”的模型。登录前只提交校园账号、学号或工号和密码，由服务端从数据库匹配唯一用户、姓名、用户编号和角色；多角色用户登录成功后可以切换当前角色。授权以当前激活角色为依据，客户端与服务端同步切换，界面只展示该职责有权操作且已经实现的功能。

| 角色 | 主要职责 | 明确不负责 |
|---|---|---|
| 学生 | 个人学籍、选课报名、借阅预约、购物、宿舍申请缴费、AI查询 | 审批和基础数据维护 |
| 任课教师 | 查看授课课程、维护本人课程成绩、申请教室 | 学籍变更、全校排课和用户授权 |
| 学籍管理员 | 学籍建档、变更、查询、成绩档案核对 | 排课、图书、商店、宿舍业务 |
| 教务老师 | 课程排期、选课管理、公告比赛、SRTP、教室审批 | 学籍基础档案、其他生活模块 |
| 图书管理员 | 图书库存、借还、自习室、线上资源和图书馆公告 | 教务和商店管理 |
| 商店管理员 | 商品、库存、订单处理和销售统计 | 用户充值授权与其他模块审批 |
| 宿管员 | 房间床位、入住调宿退宿、门禁预警、卫生、报修、水电和宿舍公告 | 学籍、教务和系统账号管理 |
| AI知识管理员 | 知识片段维护、检索质量和调用日志监控 | 代替业务管理员执行业务审批 |
| 系统管理员 | 用户、角色、系统配置、连接与运行日志 | 默认不拥有教务、图书、商店、宿舍等业务写权限 |

## 权限实施原则

1. 客户端权限用于隐藏无权菜单和按钮，服务端必须再次鉴权。
2. 服务器从会话读取用户和角色，不信任请求载荷中的用户编号或角色。
3. 系统管理员负责“谁具有某角色”，业务管理员负责“该业务如何处理”。
4. 多角色用户的审计记录必须包含实际使用的角色。
5. 数据范围必须在业务服务中约束，例如教师只能登记本人授课课程的成绩，学生只能读取自己的学籍。
