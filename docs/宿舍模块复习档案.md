### 1.2 完整请求链路（以「维修员接单」为例）

```
DormRepairWorkPanel（Swing，EDT）
  → AsyncTask.run(...)                     view/modules/real/AsyncTask.java（SwingWorker）
  → DormExtClientService.acceptRepair(...)  客户端接口
  → NetworkDormExtClientService             拼 Message.request("dorm.ext.repair.accept", token, RepairWorkRequest)
  → NetworkClientService / SocketClientGateway  ObjectOutputStream 写 Message
── Socket ──
  → ClientConnectionHandler.run()           server/network/，SafeObjectInputStream 读回 Message
  → CommandRouter.route(request)            解析 token → SessionContext，校验 Permission
  → DormExtCommandHandler.dispatch(...)     按 command 分派
  → DormExtService.acceptRepair(...)        门面
  → DormExtRepairWorkService.transition(..., Step.ACCEPT)  require(DORM_REPAIR_WORK)
  → DormServiceSupport.execute(Work)        TransactionManager 开事务
  → MySqlDormExtRepository → MySqlDormRepairWorkRepository.claim(c, orderId, handlerId)
  → UPDATE repair_orders ... WHERE id=? AND status='SUBMITTED' AND handler_id IS NULL
  ← Message.success(request, RepairWorkOrderDto)
```

### 1.3 `Message` 结构（`vcampus-common/src/main/java/edu/seu/vcampus/common/protocol/Message.java`）

`final class Message implements Serializable`，`serialVersionUID = 1L`，全部字段 `final`（除 `timestamp` 也是 final）：

| 字段 | 说明 |
|---|---|
| `requestId` | `UUID.randomUUID()`；响应用 `related()` 复制请求的 requestId，实现请求-响应配对 |
| `type` | `MessageType`：`REQUEST` / `RESPONSE` / `STREAM_CHUNK` / `ACTION_CONFIRMATION` |
| `command` | 命令字符串，如 `"dorm.ext.repair.accept"` |
| `sessionToken` | 仅请求携带；`related()` 构造响应时**置 null**，token 不回传 |
| `payload` | `Serializable`（所以 handler 里 `REPAIR_WORKERS` 要把 `List` 包成 `ArrayList` 才能发） |
| `success` / `resultCode` / `userMessage` | 结果三元组；`resultCode` 取 `ResultCodes.OK` 或 `DormCommands.*` / `DormExtCommands.*` 里的稳定码 |
| `timestamp` | `System.currentTimeMillis()` |

工厂方法：`request(command, token, payload)`、`success(request, payload)`、`failure(request, code, message)`、`stream(...)`、`action(...)`。无公开构造器。

### 1.4 Socket 传输与反序列化白名单

- 服务端 `vcampus-server/.../network/ClientConnectionHandler.run()`：
  - `socket.setTcpNoDelay(true)`、`setSoTimeout(readTimeoutMillis)`；
  - **先** `new ObjectOutputStream(...)` 并 `flush()`，**再** `new SafeObjectInputStream(socket.getInputStream())`（避免双方都阻塞在读 stream header）；
  - 循环 `input.readObject()`；非 `Message` 直接 `break` 关连接；
  - 流式命令（AI 模块）走 `commandRouter.routeStream`，宿舍命令走 `commandRouter.route`；
  - `writeMessage` 对 `output` 加 `synchronized`。
- 客户端对应 `client/network/SocketClientGateway`（持久连接）、`client/auth/AiStreamConnection`。
- `vcampus-common/.../protocol/io/SafeObjectInputStream`：
  - `resolveClass` 白名单：`edu.seu.vcampus.common.dto.*`、`common.protocol.*`、`common.ai.*`，外加 `common.security.Role` / `Permission`；JDK 侧只放 `java.lang` 包装类、`BigDecimal`/`BigInteger`、`org.threeten.bp.LocalDate/LocalDateTime/LocalTime/Ser`（Java 7 用 ThreeTen-Backport）、一批白名单集合类与 `UUID`；数组按元素类型递归校验。
  - `resolveProxyClass` **一律拒绝**。
  - 内部 `CumulativeLimitedInputStream`：默认 `MAX_STREAM_BYTES = 8MB`，注意注释明说这是**整条持久连接的累计预算**，不是单请求。

### 1.5 `CommandRouter`（`vcampus-server/.../router/CommandRouter.java`）

- `ConcurrentHashMap<String, CommandHandler> handlers`；`register(command, handler)`。
- `route(request)`：
  1. 非 `REQUEST` 或 command 空 → `ServerResultCodes.MALFORMED_REQUEST`；
  2. 未注册 → `UNKNOWN_COMMAND`；
  3. `authorize()`：若 `handler.requiresAuthentication()` 或 `requiredPermission() != null`，用 `sessionManager.resolve(token)` 拿 `SessionContext`，null → `ResultCodes.UNAUTHORIZED`「请先登录」；`!session.allows(required)` → `ResultCodes.FORBIDDEN`「当前角色无权执行此操作」；
  4. handler 返回 null → `INTERNAL_ERROR`；`RuntimeException` 记 `SEVERE` 日志后返回通用错误。

### 1.8 注册与 Handler

- `DormCommandRegistry.register(router, service)`：一个 `String[] commands` 数组，逐条 `router.register(cmd, new DormCommandHandler(cmd, service))` —— **同一个 Handler 类被实例化 38 次，每个实例记住自己的 command**。工厂方法 `createMySqlService(TransactionManager)` → `new DormService(new MySqlDormRepository(), transactions)`。
- `DormExtCommandRegistry` 同构，42 条 → `DormExtCommandHandler`。
- `ServerMain`（第 120/121、131/132、137-139 行）：创建两个 service、注册、条件性 `new DormScheduler(dormExtService)`。
- `DormCommandHandler.handle` 是一长串 `if (DormCommands.X.equals(command))`，catch 三层：`DormException` → 原样 resultCode；`IllegalArgumentException` → `DORM.INVALID_INPUT`；`RuntimeException` → 记 `SEVERE` + `DORM.INTERNAL_ERROR`。载荷用私有静态 `payload(Object, Class<T>)` 做强类型校验。
- `DormExtCommandHandler` 同构，载荷解析集中在 `DormExtPayloads`。

### 1.9 服务/仓储分层

- 门面：`DormService`（拆 7 个包私有子服务：`DormFacilityService`/`DormSpaceService`/`DormLeaveService`/`DormAccommodationService`/`DormGovernanceService`/`DormBillingService`/`DormAnnouncementService`）、`DormExtService`（拆 7 个：`DormExtMeterService`/`WarningService`/`VisitorService`/`HygieneService`/`AccessService`/`NoticeService`/`RepairWorkService`）。
- 公共基类 `DormServiceSupport`：`execute(Work<T>)` 包 `TransactionManager.execute`；`require(session, permission)`、`requireAny(...)`；`id()`/`page()`/`text()` 校验；`message(Exception)` 会把 SQLException 原话截 160 字返回并提示「多半是 scripts/apply-dorm-migrations.sql 还没跑」。
- 仓储接口：`DormRepository`（由 `DormRepositoryComposite` 组合 7 个子接口 `DormFacilityRepository`/`DormSpaceRepository`/`DormLeaveRepository`/`DormAccommodationRepository`/`DormGovernanceRepository`/`DormBillingRepository`/`DormAnnouncementRepository`）、`DormExtRepository`（92 行单接口）、`DormPaymentPort`（只有 `charge(...)` 一个方法）。
- 实现两套：`InMemoryDorm*`（全 `synchronized`，测试用）与 `mysql/MySqlDorm*`（真实 JDBC，公用 `JdbcDormSupport`/`MySqlDormExtSupport`）。
- 事务：`server/db/TransactionManager.execute` —— `setAutoCommit(false)` → work → `commit()`，异常 `rollback()` 并 `addSuppressed`，finally 恢复 autoCommit。**DAO 不得自行提交**（类注释）。

## 二、权限模型

### 2.1 `Role`（`vcampus-common/.../security/Role.java`）

10 个：`STUDENT`(学生)、`TEACHER`、`REGISTRAR`、`ACADEMIC_ADMIN`、`LIBRARIAN`、`STORE_MANAGER`、**`DORM_MANAGER`(宿管员)**、**`REPAIR_WORKER`(维修员)**、`AI_KNOWLEDGE_ADMIN`、`SYSTEM_ADMIN`。

### 2.2 `Permission` 中宿舍相关 7 条

`DORM_SELF_READ`、`DORM_REQUEST`、`DORM_BILL_PAY`、`DORM_MANAGE`、`DORM_APPROVE`、`DORM_GOVERN`、`DORM_REPAIR_WORK`

### 2.3 `RolePolicy` 映射（`buildPolicies()`）

| 角色 | 宿舍权限 | 备注 |
|---|---|---|
| `STUDENT` | `DORM_SELF_READ`、`DORM_REQUEST`、`DORM_BILL_PAY` | 另有 `STORE_PURCHASE` 等 |
| `DORM_MANAGER` | `DORM_MANAGE`、`DORM_APPROVE`、`DORM_GOVERN`，外加 `ANNOUNCEMENT_MANAGE` | 无 `DORM_SELF_READ`、无 `DORM_REQUEST`、无 `DORM_BILL_PAY` |
| `REPAIR_WORKER` | **只有 `DORM_REPAIR_WORK`**（外加 `PROFILE_READ`/`PROFILE_UPDATE`） | 源码注释：「他要进学生宿舍，但不该顺带看到住宿名册、水电账单和卫生检查。派单需要的房间号和联系方式随工单一起下发」 |

`RolePolicy` 提供 `allows(role, perm)`、`allowsAny(roles, perm)`、`permissionsOf(role)`；所有集合 `Collections.unmodifiableSet(EnumSet.of(...))`。

| `DORM_GOVERN` | `utility.manager.list`、`alert.handle`、`hygiene.list`、`hygiene.save` |
| `DORM_MANAGE` | `accommodation.assign/transfer/checkout`、`building.create/update`、`room.create/update`、`bed.create/update` |

| `DORM_BILL_PAY` | `utility.pay` |
| `ANNOUNCEMENT_MANAGE` | `announcement.save` |

`requiredPermission()` 返回 null 的那些命令，**在服务层再做二次判定**（这是本模块一个重要设计点）：
- `DormAccommodationService.requests()`：`requireAny(DORM_REQUEST, DORM_APPROVE)`，且 `manager = session.allows(DORM_APPROVE)`，非宿管强制 `student = session.getUserId()`，忽略客户端传的 studentId；
- `DormGovernanceService.access()/alerts()`：`requireAny(DORM_SELF_READ, DORM_GOVERN)`，`owner = allows(DORM_GOVERN) ? studentId : 自己`；
- `DormGovernanceService.repairs()`：同理，宿管 `owner=null`（看全部），学生只看自己；
- `DormLeaveService.mine()`：`require(DORM_SELF_READ)` 且仓储查询固定传 `session.getUserId()`。

`DormExtCommandHandler.requiredPermission()`：

| 权限 | 命令 |
|---|---|
| `DORM_REQUEST` | `visitor.submit`、`visitor.cancel`、`repair.permit.set` |
| `DORM_SELF_READ` | `visitor.mine`、`stay.mine`、`home.summary`、`access.mine`、`repair.permit.mine`、`notice.mine` |
| `DORM_MANAGE` | `room.delete` |
| `DORM_REPAIR_WORK` | `repair.queue`、`repair.assigned`、`repair.history`、`repair.accept`、`repair.start`、`repair.finish` |
| `DORM_GOVERN` | `repair.workers`、`repair.assign`、`repair.review`、`repair.detail`，以及**默认分支**（抄表、出账、预警、卫生、门禁策略、公告管理、status、scheduler.run 全部落到默认 `return Permission.DORM_GOVERN`） |
| `DORM_APPROVE` | `visitor.list`、`visitor.audit` |

### 2.5 服务端如何校验：`SessionContext`

`vcampus-server/.../security/SessionContext.java`
- 不可变字段：`sessionToken`、`userId`、`account`、`displayName`、`Set<Role> roles`（`unmodifiableSet(EnumSet.copyOf)`）、`activeRole`、`createdAt`；`volatile long lastAccessAt`（包私有 `touch()`）。
- 构造器全量校验：token 非空、`userId > 0`、至少一个角色、`activeRole` 必须属于 `roles`。
- **`allows(Permission p)` 只看 `activeRole`，不看 `roles` 全集** → `RolePolicy.allows(activeRole, p)`。多角色用户必须 `withActiveRole(role)` 切换职责才能拿到另一套权限。
- `getRole()` 是兼容方法，注释明说「服务端鉴权必须使用 `allows(Permission)`」。

**两道闸**：① `CommandRouter.authorize()` 粗粒度按 `requiredPermission()`；② 服务层 `DormServiceSupport.require/requireAny` 再查一遍（`ResultCodes.UNAUTHORIZED` / `FORBIDDEN`）。第二道不是多余：它保证服务被单测直接调用时权限规则仍生效，也支撑上文「同一命令、不同角色不同数据范围」的判定。

**归属权校验（第三道）**，散在各服务里：
- `DormGovernanceService.createRepair`：查 `findCurrent()`，`current.getRoomId() != request.getRoomId()` → FORBIDDEN「只能为本人住宿房间报修」；
- `evaluateRepair`：`old.getReporterId() != session.getUserId()` → FORBIDDEN；且要求 `COMPLETED` 且 `evaluationScore == null`（只能评一次）；
- `updateRepair`：非宿管只允许 `SUBMITTED → CANCELLED` 且必须是自己的单；
- `DormLeaveService.cancel`：`old.getStudentUserId() != s.getUserId()` → FORBIDDEN；
- `DormExtAccessService.setPermit`：`repository.repairReporterOf()` 比对本人；
- `DormExtVisitorService.cancel`：比对 `studentUserId`；
- `DormExtRepairWorkService`：`handler` 一律取 `session.getUserId()`，注释「不接受客户端传入——否则一个维修员可以把单子接到同事名下」。
- `dorm_visitor_registrations.room_id` 由服务端 `activeRoomOf(session.getUserId())` 解析，不接受客户端指定（V5 注释）。
- 客户端也帮一手：`NetworkDormClientService.myLeaveQuery()` 把调用方传的 studentId 清成 null。

## 四、业务规则

### 4.1 住宿分配与调宿审批流

**直接办理（宿管，`DORM_MANAGE`）**：`DormAccommodationService.assign / transfer / checkout` → `repository.assign/transfer/checkout(c, studentId, bedId, date, actor)`。唯一占床靠 `accommodation_records` 的两个生成列唯一键，业务码 `DORM.BED_OCCUPIED` / `DORM.ALREADY_ACCOMMODATED`。

**申请审批（学生提交 → 宿管审批）**：
1. `dorm.request.submit`（`DORM_REQUEST`）→ `submit()`：`requestType` 大写归一；`CHECK_OUT` 强制把 `requestedBedId` 置 null；**学生不填床位**（V9）。
2. `dorm.request.list`：`requireAny(DORM_REQUEST, DORM_APPROVE)`；非宿管强制只看自己。
3. `dorm.request.approve`（`DORM_APPROVE`）→ `approve()`，在一个事务里：
   - `repository.lockRequest(id)`（SELECT ... FOR UPDATE）→ null 则 `DORM.REQUEST_NOT_FOUND`；
   - 非 `PENDING` → `DORM.REQUEST_INVALID_STATE`「申请已处理」；
   - 若通过，`bedOf(request, pending)`：**优先用宿管当场点的 `request.getBedId()`**，回落到申请单上的 `requestedBedId`（仅历史数据有值）；
   - `apply()`：非 CHECK_OUT 且 bed 为 null → `DORM.INVALID_INPUT`「请先为这条申请指定床位，再点通过」（注释：不能放行「已通过但没落实」的申请）；按 type 调 `assign` / `transfer` / `checkout`，生效日一律 `LocalDate.now()`；
   - `repository.finishRequest(id, actor, approved, remark)` 写审批结果。

### 4.2 请假/离校（`DormLeaveService`）

- 时间段语义：**`[start, end)` 重叠**（类注释）。
- `submit`：`require(DORM_REQUEST)`；`submitRequest()` 校验时间非空、`end > start`、`leaveType` 必须能 `DormLeaveType.valueOf`、`reason` 必填且 ≤500；然后 `serialized(...)` 里 `repository.lockStudent(userId)` → `hasOverlap(...)` → `DORM.LEAVE_OVERLAP`「请假时间与已有申请重叠」→ `submit`。
- `cancel`：锁记录 → 不存在 `DORM.LEAVE_NOT_FOUND` → 归属校验 FORBIDDEN → `cancel`。
- `review`（`DORM_APPROVE`）：备注 ≤500；锁记录；非 `PENDING` → `DORM.LEAVE_INVALID_STATE`「仅待审核申请可以审核」；**若 approved 再锁学生并重查一次重叠**（防止两条互相重叠的申请被分别批准）。
- `dorm.leave.approve` / `dorm.leave.reject` 是 `leave.review` 的糖：Handler 的 `review(p, approved)` 会校验 `request.isApproved() == approved`，不一致直接 `IllegalArgumentException`（「review action mismatch」），也接受 `DormApprovalRequest` 并转成 `LeaveReviewRequest`。
- `serialized(Work)`：`transactions == null`（内存模式）时 `synchronized (repository)`，否则依赖数据库行锁。

### 4.3 晚归 vs 连续未归（两套，不要混）

**(a) 晚归 `late_return_alerts`（V1，dorm 主模块）**
- `dorm.access.record`（`requireAny(DORM_REQUEST, DORM_GOVERN)`）：`studentUserId` 一律取会话，不接受客户端；
- `dorm.alert.list`（自己/宿管全量）、`dorm.alert.handle`（`DORM_GOVERN`）→ `DormGovernanceService.handleAlert`；
- 晚归**不落库标记**，由 `DormStayRules.isLateReturn(recordType, occurredAt, curfew, dawn)` 按策略实时判定：仅 `ENTRY` 记录可能晚归；`!time.isBefore(curfew) || time.isBefore(dawn)` 为真即晚归。注释解释 `dawn` 的必要性：「凌晨两点回来在时钟上『早』，在管理上是整夜未归」。
- 策略校验 `DormExtAccessService.savePolicy`：`dawn` 必须早于 `curfew`，否则 `DORM_EXT.POLICY_INVALID`「否则整天都会被判成晚归」。

**(b) 连续未归 `dorm_absence_warnings`（V5，ext 模块）**
- 纯函数 `DormAbsenceRules`：
  - `absenceDays(lastExitAt, lastEntryAt, scanDate)`：`lastExitAt` 为 null → 0；`lastEntryAt != null && !lastEntryAt.isBefore(lastExitAt)` → 0（已回来）；否则 `ChronoUnit.DAYS.between(lastExitAt.toLocalDate(), scanDate)`，`<=0` 记 0（当天离当天扫不算未归）；
  - `shouldWarn(days, warnDays)`：`warnDays>0 && days >= warnDays`；
  - `level(days, notifyDays, onApprovedLeave)`：**已批准请假优先** → `LEVEL_EXEMPT`；否则 `days >= notifyDays` → `LEVEL_SEVERE`，else `LEVEL_NORMAL`。
- `DormExtWarningService.scan(c, date)`：`loadWarningConfig` → `residentsForScan()` 拿 `ResidentAbsenceSnapshot` 列表 → 逐人算天数 → 未达阈值 `continue` → `config.isExemptOnLeave() && hasApprovedLeave(student, date)` → 定级 → `saveWarning(...)`（靠 UNIQUE(student,scan_date) 幂等）→ 计数返回 `WarningScanResultDto(date, 扫描人数, normal, severe, exempt)`。
- 处理状态机 PENDING → NOTIFIED → VERIFIED：
  - `notify`：必须带 `teacherUserId`（否则 INVALID_INPUT「请指定要通知的辅导员」）；若已 VERIFIED → `DORM_EXT.WARNING_INVALID_STATE`「该预警已核实，无需再通知」；
  - `verify`：不校验是否已通知，**可以从 PENDING 直接 VERIFIED**，并沿用当前记录的 `notifiedTeacherId`/`notifiedAt`（可能为 null，与表 CHECK 一致因为状态不是 NOTIFIED）。
- `saveConfig`：`warnDays<=0` → CONFIG_INVALID「预警天数必须大于零」；`notifyDays < warnDays` → 「通知天数不能小于预警天数」。
- `DormStayRules.status(lastExitAt, lastEntryAt, onApprovedLeave)`：请假 → `LEAVE_REGISTERED`；无离宿记录 → `IN_DORM`；最后归宿不早于最后离宿 → `IN_DORM`；否则 `OUT`。在 `DormExtAccessService.resolve()` 里对每一行重算（**逐行调 `hasApprovedLeave`，N+1 查询**）。

### 4.4 卫生检查打分与打回重做

**纯函数 `DormHygieneRules`**：
- 常量：`RECTIFY_THRESHOLD = 70`、`RECHECK_AFTER_DAYS = 3`。
- `validate(items)`：必须**五项齐全**（`HygieneItemScoreDto.ITEM_CODES.length`）、编码已知、**不重复**（HashSet）、每项 `0 ~ MAX_ITEM_SCORE(20)`。注释：「缺项会让总分凭空变低，重复项会让总分超过 100」。
- `total(items)` = 五项之和（BigDecimal）。
- `level(total)`：≥90 `LEVEL_EXCELLENT`，≥80 `LEVEL_GOOD`，≥60 `LEVEL_PASS`，else `LEVEL_POOR`。
- `needRectify(total)`：`total < 70`。
- `result(total)`：映射到 V1 的两态 → `FAIL` / `PASS`（注意：**60~69 分的 level 是「合格」但 result 是 FAIL**，因为整改线 70 和合格线 60 不同）。
- `status(total)`：`RECTIFICATION_REQUIRED` / `NORMAL`。
- `recheckDate(inspectedOn)` = `inspectedOn.plusDays(3)`。

**`DormExtHygieneService.submit`（`DORM_GOVERN`，一个事务）**：
`total` → `createInspection(room, inspector=session.getUserId(), now, total, result, status, issueDescription)` → `saveItemScores(id, items)` → `markTasksDone(room, today, id)`（把当天该房间的 PENDING 任务置 DONE 并回填 inspection_id）→ **若 `needRectify`** 则 `createTaskIfAbsent(room, TYPE_RECHECK, recheckDate, sourceInspectionId=id)` → 返回 `findInspectionDetail(id)`。这就是「打回重做」：不合格自动排一张 3 天后的 RECHECK 任务。
校验失败走 `DORM_EXT.HYGIENE_ITEMS_INVALID`（把 `IllegalArgumentException` 的 message 直接带给用户）。

**周任务 `generate(c, request)`**：`planDate` 默认今天，`buildingId` 可为 null（全部楼）→ `roomsForWeeklyTask(building)` → 逐间 `createTaskIfAbsent(..., TYPE_WEEKLY, date, null)`，返回 `HygieneTaskGenerateResultDto(date, roomsScanned, created, existing = scanned - created)`。幂等靠 UNIQUE(room,plan_date,task_type)。

> 另有 **主模块**的简版：`dorm.hygiene.save` → `DormGovernanceService.saveHygiene`，只校验 `score` 0~100 与 `result` 非空，直接写 `hygiene_inspections`，无分项、无自动复查。宿管端两者并排（历史记录 vs 待检任务+分项打分）。

### 4.5 水电抄表 → 账单拆分 → 缴费 → 商店余额

**抄表（`DORM_GOVERN`）**：`dorm.ext.meter.submit` → `DormExtMeterService.save` → `DormExtValidation.meter(request)` → `repository.saveMeterReading(c, r, session.getUserId())`。表上 UNIQUE(room,period) 使之成为「录入或更新」；`bill_id` 非空即锁定（`DORM_EXT.METER_LOCKED`）。

**出账 `dorm.ext.bill.generate`（`DormExtMeterService.generate`，单事务）**：
1. `due` = 请求给的 `dueAt`，否则 `periodEnd.plusDays(15).atTime(23,59)`（`DEFAULT_DUE_DAYS = 15`）；
2. `pendingReadings(roomId, periodStart, periodEnd)`（`bill_id IS NULL` 的读数）；空 → `DORM_EXT.NO_PENDING_READING`；
3. 逐条读数：
   - `billExists(room, period)` → 跳过，记「该账期已有账单，跳过」；
   - `activeResidents(room)` 空 → 跳过「无在住学生」；
   - `amount = reading.getTotalAmount().setScale(2, HALF_UP)`；
   - `!DormBillSplit.isSplittable(amount, n)` → 跳过「应缴 X 元不足以按 n 人分摊」（因为 `utility_allocations.amount > 0`）；
   - `createBill(...)` → `DormBillSplit.split(amount, n)` → 逐人 `createAllocation(bill, studentId, share)` → `linkReadingToBill(readingId, billId)`（锁定读数）；
4. 返回 `BillGenerateResultDto(bills, shares, skipped, total, notes)`，`notes` 是给宿管看的逐房间说明。

**`DormBillSplit`（拆分算法，纯函数）**：
- `isSplittable(total, shares)`：`total >= 0.01 * shares`。
- `split(total, shares)`：`base = amount.divide(shares, 2, RoundingMode.DOWN)` → `extraCents = (amount - base*shares) * 100` → **前 `extraCents` 个人各加 1 分**。类注释：「分摊结果必须精确等于房间总额……因此不会出现四舍五入后合计对不上总额的账」。

**缴费 `dorm.utility.pay`（`DORM_BILL_PAY`）**：
- `DormBillingService.pay`：`allocationId` 校验、**`idempotencyKey` 必填且 trim**，否则 `DORM.INVALID_INPUT`；
- `MySqlDormBillingRepository.pay(c, student, request)`（同一事务内）：
  1. `lockAllocation(c, student, allocationId)`（含归属，SELECT ... FOR UPDATE）；
  2. 状态 `PAID` → `DORM.BILL_ALREADY_PAID`；非 `UNPAID` → `DORM.BILL_NOT_PAYABLE`；
  3. `payments.charge(...)` —— `DormPaymentPort`；
  4. `UPDATE utility_allocations SET status='PAID', paid_transaction_id=?, paid_at=NOW() WHERE id=? AND status='UNPAID'`，影响行 ≠1 → `DORM.PAYMENT_DUPLICATE`；
  5. 汇总账单状态：`UPDATE utility_bills SET status = CASE WHEN NOT EXISTS(SELECT 1 FROM utility_allocations WHERE bill_id=? AND status='UNPAID') THEN 'PAID' ELSE 'PARTIAL' END WHERE id=?`。

**`DormPaymentPort` 与商店余额的联动**：接口只有一个方法
`long charge(Connection connection, long userId, BigDecimal amount, String idempotencyKey, long allocationId)` —— 注释「宿舍对账户能力的最小边界，**不依赖 store 服务包**」。
实现 `MySqlDormPaymentAdapter`（`repository/mysql/`），只碰 `accounts` / `account_transactions`：
1. 先查 `account_transactions WHERE idempotency_key=?`，命中 → `DORM.PAYMENT_DUPLICATE`；
2. `SELECT id, balance FROM accounts WHERE user_id=? AND status='ACTIVE' FOR UPDATE`，无行 → `DORM.BILL_NOT_PAYABLE`「账户不可用」；
3. 余额不足 → `DORM.BILL_NOT_PAYABLE`「账户余额不足」；
4. **乐观 + 悲观双保险**：`UPDATE accounts SET balance=?, version=version+1 WHERE id=? AND balance=?`，≠1 → 「账户余额发生变化，请重试」；
5. `INSERT account_transactions(... transaction_type='DORM_BILL_PAYMENT', amount = -amount, balance_before, balance_after, reference_type='UTILITY_ALLOCATION', reference_id=allocationId, idempotency_key, operator_id=userId, remark='宿舍水电分摊')`，返回自增 id 写回 `paid_transaction_id`。

因此宿舍缴费直接扣一卡通/商店余额，且账户流水里带 `reference_type='UTILITY_ALLOCATION'` 可对账。V1 注释也提到 `account_transactions.idempotency_key` 提供「exact-once 应用保证」。

### 4.6 报修工单状态机（完整六态）

**数据库取值**（V1 + V8）：`SUBMITTED`、`ACCEPTED`、`IN_PROGRESS`、`PENDING_REVIEW`、`COMPLETED`、`CANCELLED`。
**⚠️ 枚举 `DormRepairStatus`（common/dto/dorm/）只列了 5 个，缺 `PENDING_REVIEW`** —— 见第八节弱点 1。

**全链路（`DormExtRepairWorkService` + `MySqlDormRepairWorkRepository`）**：

| 步骤 | 角色/权限 | 命令 | SQL 转移条件 | 结果 |
|---|---|---|---|---|
| 学生报修 | `DORM_REQUEST` | `dorm.repair.create` | `DormGovernanceService.createRepair` 先校验 `findCurrent().roomId == request.roomId` | → `SUBMITTED` |
| 学生授权入内 | `DORM_REQUEST` | `dorm.ext.repair.permit.set` | 校验本人是 reporter；**若 `allowEnter` 且账号无手机号且备注为空** → `DORM_EXT.CONTACT_REQUIRED` | 写 `dorm_repair_entry_permits` |
| 学生取消 | `DORM_REQUEST` | `dorm.repair.update` | 非宿管只允许 `SUBMITTED → CANCELLED` 且是自己的单 | → `CANCELLED` |
| **宿管派单** | `DORM_GOVERN` | `dorm.ext.repair.assign` | `UPDATE ... SET handler_id=?, status = CASE WHEN status='SUBMITTED' THEN 'ACCEPTED' ELSE status END, accepted_at=COALESCE(accepted_at, NOW()) WHERE id=? AND status IN ('SUBMITTED','ACCEPTED','IN_PROGRESS')` | 可改派；已 COMPLETED/CANCELLED 不可（0 行 → `REPAIR_INVALID_STATE`「工单已经完工/取消，不能再派单」） |
| 维修员接单 | `DORM_REPAIR_WORK` | `dorm.ext.repair.accept` | `SET handler_id=?, status='ACCEPTED', accepted_at=NOW() WHERE id=? AND status='SUBMITTED' AND handler_id IS NULL` | 0 行 → `REPAIR_ALREADY_TAKEN`「该工单已被其他维修员接走」 |
| 维修员开工 | `DORM_REPAIR_WORK` | `dorm.ext.repair.start` | `SET status='IN_PROGRESS' WHERE id=? AND handler_id=? AND status='ACCEPTED'` | |
| 维修员报完工 | `DORM_REPAIR_WORK` | `dorm.ext.repair.finish` | `SET status='PENDING_REVIEW' WHERE id=? AND handler_id=? AND status IN ('ACCEPTED','IN_PROGRESS')` | **不写 `completed_at`**（注释：那记的是真正了结的时间） |
| **宿管审核** | `DORM_GOVERN` | `dorm.ext.repair.review` | 通过：`SET status='COMPLETED', completed_at=NOW() WHERE id=? AND status='PENDING_REVIEW'`；打回：`SET status='IN_PROGRESS' WHERE id=? AND status='PENDING_REVIEW'` | 打回后由**同一个维修员**继续（handler_id 不变） |
| 学生评价 | `DORM_REQUEST` | `dorm.repair.evaluate` | 必须 reporter 本人、`status='COMPLETED'`、`evaluationScore == null`；分数 1~5，备注 ≤500 | 只能评一次 |

**并发设计要点（考点）**：三个维修员写操作**全部是「带条件的 UPDATE」，不是「先查后改」**。类注释写得很明确：「接单是两个维修员会同时点的按钮，先查再改中间隔着一次网络往返，两个人都会读到『还没人接』然后双双写进去，后写的把前一个人的名字覆盖掉。把前置条件放进 WHERE，数据库自己保证只有一次更新会命中，返回的受影响行数就是『抢到没有』」。

**失败原因回查 `reject(c, orderId, handler, step)`**：更新 0 行后回查一次，区分三种情况给不同提示 —— 单不存在（`REPAIR_NOT_FOUND`）、被同事接走 / 不是自己的单（`REPAIR_ALREADY_TAKEN`）、状态不允许（`REPAIR_INVALID_STATE`）。注释：「统一回一句『操作失败』会让人反复点同一个按钮」。

**维修员没有「退回」动作**（类注释）：「工单退回涉及重新派单和对学生的解释，属于宿管的职责，维修员单方面把单子扔回队列会让它在两边之间反复横跳」。

**队列与排序**：
- `queue`：`WHERE o.status='SUBMITTED' AND o.handler_id IS NULL`；
- `assigned(active=true)`：`handler_id=? AND status IN ('ACCEPTED','IN_PROGRESS')`；
- `assigned(active=false)`（历史）：`status IN ('PENDING_REVIEW','COMPLETED','CANCELLED')` —— 报完工的单归「处理记录」侧；
- 优先级排序 `priorityOrder()`：`ORDER BY FIELD(o.priority,'URGENT','HIGH','NORMAL','LOW'), o.submitted_at ASC, o.id ASC`；历史按 `completed_at DESC, id DESC`。

**隐私：联系电话逐行决定**。`COLUMNS` 里带 `u.phone AS contact_phone`，但 `row(r, withPhone)` 决定是否放进 DTO：
- 队列（`reader(false)`）不给电话；
- 在手工单（`reader(true)`）给；
- `find(orderId, handlerId)` 用 `HandlerAwareReader`：`handler == handlerId` 才给；
- 宿管 `findForManager` 直接给（注释「派单本来就要联系人」）。

**可派单维修员 `workers(c)`**：`users JOIN user_roles JOIN roles(code='REPAIR_WORKER') LEFT JOIN repair_orders ON handler_id=u.id AND status IN ('ACCEPTED','IN_PROGRESS')`，`WHERE u.status='ACTIVE'`，`GROUP BY`，`ORDER BY active_orders ASC, display_name ASC`（在手少的排前面，方便负载均衡派单）。注释解释为何不先查人再逐个查单：往返次数与中间状态不同步。

**`repair.review` 的一个实现细节（Handler 层）**：通过与打回**共用一条命令**，用 `RepairWorkRequest.getNote()` 携带判定 —— `"REJECT".equals(note)` 即打回，其余为通过。源码注释：「两个动作的入参完全一样，分成两条命令只是多一份登记」。

### 4.7 访客登记与门禁

**访客（`DormExtVisitorService`）**：
- `submit`（`DORM_REQUEST`）：`DormExtValidation.visitor(r)` → `activeRoomOf(session.getUserId())`，无在住记录 → `DORM_EXT.NO_ACCOMMODATION`「没有有效的住宿记录，无法登记来访人员」→ `createVisitor(c, studentId, roomId, r)`。**room_id 服务端解析，防止登记到别人房间**。
- `own`（`DORM_SELF_READ`，固定自己）/ `list`（`DORM_APPROVE`，全量）。
- `cancel`（`DORM_REQUEST`）：本人 + `isPending()`，否则 `VISITOR_INVALID_STATE`「只有待审核的登记可以撤销」→ `STATUS_CANCELLED`。
- `audit`（`DORM_APPROVE`）：`isPending()` 否则「该登记已处理，不能重复审核」→ APPROVED/REJECTED，写 `auditorId` + `LocalDateTime.now()` + remark。
- **证件脱敏**：`VisitorRegistrationDto.mask(idCard)` —— 保留前 3 后 2，中间全 `*`。在**仓储读出时就脱敏**（`MySqlDormExtSupport` 第 30 行、`InMemoryDormVisitorStore` 第 21 行），明文只留在库里。

**门禁（`DormExtAccessService`）**：
- `access.mine`（`DORM_SELF_READ`）：`listAccessRecords(c, userId, q, loadAccessPolicy(c))` —— 策略作为参数下传，晚归实时判定；
- `access.policy.get/set`（`DORM_GOVERN`）：`savePolicy` 强制 `dawn < curfew`；
- `stay.mine`（`DORM_SELF_READ`）：无住宿记录 → `NO_ACCOMMODATION`；
- `stay.list`（`DORM_GOVERN`）：一次性返回全部，包成 `new DormPage<>(1, max(size,1), size, rows)`（**不真分页**）；
- `home.summary`（`DORM_SELF_READ`）：住宿 / 同寝人数 / 未缴水电 / 最近一次卫生检查。无记录**不抛异常**，返回 `DormHomeSummaryDto.empty()`（注释：「新生还没分配床位时首屏照样要能打开」）；
- `room.delete`（`DORM_MANAGE`）：两道前置 —— `activeResidentCount > 0` → `ROOM_OCCUPIED`；`roomReferenceCount > 0` → `ROOM_HAS_HISTORY`「如需停用请把房间状态改为已关闭」。

**公告（`DormExtNoticeService`）**：`notice.mine` 按 `activeRoomOf` 命中范围过滤；`notice.list`（`DORM_GOVERN`）全量；`notice.extra.set` 的 `validate()` 逐一校验 type 五取值、scope 组合（ALL 不得带目标 / BUILDING 必须带楼且不得带房 / ROOM 必须带房），错码 `NOTICE_SCOPE_INVALID`，与 V5 的 `ck_dorm_notice_extras_scope_target` 一致。

### 4.8 定时任务 `DormScheduler`

`vcampus-server/.../dorm/ext/schedule/`，四个类：`DormScheduler`（实现 `DormTaskRunner`）、`DormSchedulerJobs`（作业定义）、`DormSchedulerJobDefinition`（`name/schedule/plan/task` 四元组）、`DormScheduleTimes`（时间计算纯函数）；台账在 `service/DormSchedulerStatus`。

**机制**：`Executors.newSingleThreadScheduledExecutor`，线程名 `vcampus-dorm-scheduler`，`setDaemon(true)`。**one-shot 自重排**：`Job.run()` = `execute(); schedule(this);`，每次跑完重新算下一次 `delay = DormScheduleTimes.millisBetween(now, plan.next(now))`。开关：系统属性 `vcampus.dorm.scheduler.enabled`（默认 true）、`vcampus.dorm.scheduler.operator`（记账人 userId）。

**`DormScheduleTimes`** 三个纯函数，都保证返回**严格晚于 now**（注释：避免「当前时刻正好等于计划时刻」在同一秒连跑两次）：`nextDaily`、`nextWeekly`（最多推 7 天必命中）、`nextMonthly`（`dayOfMonth` 超当月天数时落到 `lengthOfMonth()`，所以 31 号的月度任务 2 月在 28/29 号跑，而不是整月跳过）。

**五个 job（`DormSchedulerJobs.create`）**：

| 任务名常量 | 时间 | 干什么 |
|---|---|---|
| `DormSchedulerStatus.TASK_ABSENCE_SCAN` = `"absenceScan"` | **每日 08:00** | `service.runAbsenceScan(LocalDate.now())`；摘要「扫描 N 人，预警 M 条（一般/严重/免除）」 |
| `TASK_WARNING_NOTIFY` = `"warningNotify"` | **每日 08:10** | `pendingSevereWarnings(today)` → `warningSummary()` 拼「待通知严重未归 N 条：楼房/学号(X天)…」，最多列 5 条加「等」。**只生成摘要文本，不真发通知** |
| `TASK_HYGIENE_TASK` = `"hygieneTaskGenerate"` | **每周一 09:00** | `runHygieneTaskGenerate(new HygieneTaskGenerateRequest(null, today))`，全楼 |
| `TASK_NOTICE_EXPIRE` = `"noticeExpireScan"` | **每日 00:00**（`LocalTime.MIDNIGHT`） | `runNoticeExpireScan(now)` 下架过期公告 |
| `TASK_BILL_GENERATE` = `"billGenerate"` | **每月 1 日 09:00** | 账期 = 上月 1 日 ~ 上月末（`first.minusMonths(1)` ~ `first.minusDays(1)`）；`operator == null` 时抛 `DormScheduler.Skipped`「未配置 vcampus.dorm.scheduler.operator，无法确定记账人」 |

**异常分级（`Job.execute`）**：`Skipped` → `recordSkipped` + INFO；`DormException` 且 code 为 `NO_PENDING_READING` → 也算 **skipped**（没读数不是故障）；其余 `DormException` → `recordFailure(code + message)` + WARNING；`RuntimeException` → `recordFailure` + WARNING。**注意任何一档都不会中断重排**（`run()` 里 `execute()` 已捕获全部）。

**手动触发**：`dorm.ext.scheduler.run`（`DORM_GOVERN`）→ `DormExtService.runScheduledTask(session, taskName)`；runner 未挂（`attachTaskRunner` 没调）→ `DORM_EXT.SCHEDULER_UNAVAILABLE`；taskName 空 = 全跑；未知名字 → `INVALID_INPUT`「未知的定时任务：X」。
**运行状态**：`dorm.ext.status` → `DormExtStatusDto(MODULE_VERSION="dorm-ext/P6", running, describe(), now)`。

### 5.2 `DormUi`（`view/modules/real/DormUi.java`）

宿舍模块专用排版工具，把「不用卡片」的规则固定下来：内容直接铺在页面底色上，靠分隔线与留白分区，只有表单和要拎出来的提示才围半透明方框。
- 常量：`TABLE_MIN_ROWS = 5`（一两行的表夹在标题和分页条中间「看着像还没加载完」，统一垫五行）；`PANEL_FILL = (255,255,255,140)`（白 55%）、`PANEL_BORDER = 0xDFE6E0`、`ACCENT_FILL = (0xF0,0xF3,0xE9,190)`。
- 核心 `flatten(Component root)`：页面搭好后**统一走一遍组件树**改扁平形态 —— `AsyncPagedTable` 设 `setMinVisibleRows(5)` + `setColumnsFill(true)`；`SectionCard` 调 `card.flatten(seenSection)`（第一个分区不画上方分隔线）；表格与滚动面板换成页面底色、列头退灰字；其余白底面板改透明。设计理由写在注释里：「与其把二十多个面板逐个重写，不如统一走一遍组件树」，且「形态是每个实例自己的开关」，不影响其他模块。

### 5.3 `DormRoomPlan`（四人寝平面图）

`extends JPanel`，`setOpaque(false)`，尺寸 `392 × (296+26)`。

- **为什么要图**（类注释）：「床位表能回答『3 号床有没有人』，但回答不了『还剩哪张床、在靠窗还是靠门』——而宿管分配床位时想的正是后者」。
- **怎么画**：按真实户型摆 —— 窗在外墙，两侧各两张床，中间过道，卫生间和门在里侧。**实心绿 = 已占用，虚线框 = 空闲**。配色 `WALL=0xB9C6BC`、`ROOM_FILL=(255,255,255,120)`、`FREE_FILL=(255,255,255,170)`、`SOFT=0xDFE6E0`。
- **只画四人寝**：其他户型退回文字说明（`caption`），注释「画错的图比没有图更误导人」。
- **可点选**：`java.awt.Rectangle[] slots = new Rectangle[4]` 记四张床的矩形；`MouseAdapter.mousePressed` → `pick(point)` 命中后 `picked = bed; repaint(); listener.onBedPicked(bed)`；`interface Listener { void onBedPicked(DormBedDto bed); }`，宿管端用它把床位编号填进分配表单。
- `showRoom(caption, beds)` 换房间：床位按 `bedNo` 自然序排，1/2 在左、3/4 在右。

### 5.4 `DormTabs`

工厂方法 `create()` 返回一条定制外观的 `TaskTabs`：`setFont(DesignTokens.regular(14))`（标签是导航不是正文，用界面主字体，不用 `TaskTabs` 默认的衬线）+ `setUI(new PillTabUi())`。

`PillTabUi extends BasicTabbedPaneUI`：选中项画成**实心圆角块**（`GAP=4`、`RADIUS=9`，`fillRoundRect`，色 `DesignTokens.PRIMARY`，hover 用 `PRIMARY_LIGHT`），选中文字白色 + `DesignTokens.medium()`，未选中 `TEXT_SECONDARY`；`paintTabBorder`/`paintFocusIndicator`/`paintContentBorder` 全部**空实现**（去掉基线与边框）。`getTabInsets = (10,22,10,22)`。

设计理由（注释）：「同一个人在同一屏上看到的两处『我在哪儿』，没有理由长成两种样子——左边是绿底白字，上面却是灰字加一道下划线，眼睛得学两遍」；换成圆角块后不再需要基线，「块本身已经把选中项分出来了，再加一条横线就是两套指示同时开着」。
做成**工厂而非子类**：`TaskTabs` 是 final，且「换外观本来就是 setUI 的事」。

### 5.5 `AsyncTask`

`view/modules/real/AsyncTask.java`，「Swing 网络任务边界：后台执行，完成回调始终回到 EDT」。
- 两个接口：`Work<T> { T run() throws Exception; }`、`Callback<T> { onSuccess(T); onFailure(Throwable); }`。
- `run(work, callback)`：`new SwingWorker<T,Void>(){ doInBackground → work.run(); done → callback.onSuccess(get()) }`，捕获 `InterruptedException`（重设中断标志）、`ExecutionException`（**解包 `getCause()`**）、其余 `Exception`。`done()` 在 EDT 上执行，所以回调可直接改 UI。
- `message(Throwable)`：逐层 `getCause()` 找第一条非空 message；`clean()` 去掉换行、并用正则 `[A-Za-z_$][\w$]*(?:\.[A-Za-z_$][\w$]*)+` 识别并**剥掉前缀的类全名**（否则界面上会出现 `edu.seu...Exception: xxx`）；兜底「请求失败，请稍后重试。」。
- 相关：`AsyncPagedTable`（配合 `DormPage`/`DormPageQuery` 的分页表）、`DormTables`、`DormFormUi`、`DormDateField`/`DormDateTimeField`。

### 5.6 设计规范 `DesignTokens`（`client/ui/DesignTokens.java`）

- 主色系：`PRIMARY = #607830`（橄榄绿）、`PRIMARY_HOVER #728748`、`PRIMARY_PRESSED #4F6228`、`PRIMARY_LIGHT #F0F3E9`、`PRIMARY_BORDER #C7D0B1`、`GOLD #C8A75D`。
- 中性：`PAGE_BACKGROUND #F4F6F2`、`CARD_BACKGROUND` 白、`TEXT_PRIMARY #242A20`、`TEXT_SECONDARY #687063`、`TEXT_PLACEHOLDER #9AA5A0`、`BORDER #D9E1DD`、`BORDER_LIGHT #EAEFEC`。

## 七、老师最可能追问的 10 个问题 + 代码依据

**Q1：宿舍模块一共多少条命令？为什么要分 `DormCommands` 和 `DormExtCommands` 两个类？**
38 + 42 = 80 条。`DormExtCommands` 类注释给了答案：扩展命令统一用 `dorm.ext.` 前缀，「不会与既有 38 个宿舍命令重号，也不需要改动原有登记类」—— 让扩展工作不触碰已经通过测试的基线登记表。同理 V5 只新建 `dorm_` 前缀表、不改 V1 任何表结构。

**Q2：`SafeObjectInputStream` 防的是什么？光有白名单够吗？**
防 Java 原生反序列化的任意类实例化（gadget chain）：`resolveClass` 只放 `common.dto.*`/`common.protocol.*`/`common.ai.*` + `Role`/`Permission` + 一小批 JDK 值类型与集合；`resolveProxyClass` 一律拒绝（动态代理是经典利用面）。另有 `CumulativeLimitedInputStream` 8MB 预算防解压/膨胀型 DoS。不够的地方：预算是**整条持久连接累计**的，不是单请求，长连接会慢慢逼近上限；且传输仍是明文 TCP，没有 TLS。

**Q3：两个维修员同时点「接单」会怎样？**
只有一个成功。`MySqlDormRepairWorkRepository.claim` 是带条件的 UPDATE：`WHERE id=? AND status='SUBMITTED' AND handler_id IS NULL`，数据库行锁保证只有一次更新命中，`executeUpdate()` 返回 1 = 抢到、0 = 没抢到；失败方走 `reject()` 回查后得到 `DORM_EXT.REPAIR_ALREADY_TAKEN`「该工单已被其他维修员接走」。类注释明确否决了「先查后改」写法。

**Q4：报修工单一共几个状态？`PENDING_REVIEW` 为什么要加？**
六态：SUBMITTED / ACCEPTED / IN_PROGRESS / PENDING_REVIEW / COMPLETED / CANCELLED。V8 注释：原来四态里维修员一点完工就直接终结，宿管没有复核机会，而现实里「报修完没完，是宿管去看一眼才算数」。所以在 IN_PROGRESS 与 COMPLETED 之间插一态：`finish` 写 PENDING_REVIEW 且**不写 `completed_at`**，审核通过才写 COMPLETED + `completed_at`，打回则退回 IN_PROGRESS 由同一维修员继续。这样 `ck_repair_orders_completed_at` 的语义（completed_at 记真正了结时间）保持不变。

**Q5：为什么维修员只给 `DORM_REPAIR_WORK` 一条权限？他怎么知道去哪间房、联系谁？**
`RolePolicy` 和 V7 迁移的注释是同一句话：他要进学生宿舍干活，但不该顺带看到住宿名册、水电账单、卫生检查。房间号与联系电话**随工单一起下发**（`MySqlDormRepairWorkRepository.COLUMNS` 里带 `building_name`/`room_no`/`contact_phone`），而不是让他自己查全楼花名册。而且电话是逐行授予的：队列里不给（`reader(false)`），只有派给自己的单才给（`HandlerAwareReader` 比对 `handler_id == handlerId`）。

**Q6：水电账单怎么保证分摊合计等于房间总额？不足一分怎么办？**
`DormBillSplit.split`：先 `RoundingMode.DOWN` 按分均分得 `base`，算出余数 `extraCents = (amount - base*shares)*100`，把这几分**逐分补给排在前面的人**，所以合计精确等于总额，不会出现四舍五入对不上。若 `total < 0.01 * shares`（`isSplittable` 为 false）则**不出账**，`DormExtMeterService.generate` 跳过并在 `notes` 里写原因 —— 根因是 `utility_allocations` 有 `amount > 0` 的 CHECK 约束。

**Q7：宿舍缴费怎么跟商店余额打通？为什么要 `DormPaymentPort` 这个接口？**
`DormPaymentPort` 只有一个 `charge(...)` 方法，注释「宿舍对账户能力的最小边界，不依赖 store 服务包」—— 解耦，宿舍不 import 商店服务。实现 `MySqlDormPaymentAdapter` 只碰 `accounts` / `account_transactions`：查幂等键 → `SELECT ... FOR UPDATE` 锁账户 → 余额校验 → `UPDATE accounts ... WHERE id=? AND balance=?`（乐观 CAS，双保险）→ 插一条 `DORM_BILL_PAYMENT` 流水（`reference_type='UTILITY_ALLOCATION'`，负数 amount），返回的流水 id 写回 `utility_allocations.paid_transaction_id`。整链在 `TransactionManager` 的同一个事务内。

**Q8：晚归和连续未归是不是一回事？为什么建两张表？**
不是。V5 注释写得最清楚：`late_return_alerts`（V1）记的是**晚归**——回来了但超时；`dorm_absence_warnings`（V5）记的是**连续未归**——一直没回来。语义不同、状态机不同（OPEN/CONFIRMED/CLEARED/IGNORED vs PENDING/NOTIFIED/VERIFIED），所以独立建表，不改动也不复用既有表。宿管端「未归管理」页把两者并排，互补不重复。

**Q9：为什么不给 `access_records` 加一列 `is_late_return`？**
V5 `dorm_access_policies` 的注释：晚归与否完全由「归宿时刻 + 门禁时间」两者决定。存成列意味着门禁时间一改，历史记录的标记就与新策略对不上。改成按策略实时判定（`DormStayRules.isLateReturn`，策略从 `dorm_access_policies` 单行表读，作为参数下传给仓储查询），历史记录永远自洽。同理在宿状态也不落库（`DormStayRules.status`），「状态存一份就会和流水打架」。

**Q10：定时任务有几个？如果服务重启或某个任务抛异常了会怎样？**
五个（见 4.8 表）。调度用单线程 `ScheduledExecutorService` + **one-shot 自重排**（`Job.run()` 跑完再算下一次），`DormScheduleTimes` 保证下一次严格晚于当前，不会同一秒连跑两次。异常分三档：`Skipped`（如未配 operator）与 `NO_PENDING_READING` 记为 skipped，其余记 failure，**任何一档都不中断重排**。重启则全部计划丢失、按当前时刻重排（无持久化），漏掉的一次不会补跑 —— 但可用 `dorm.ext.scheduler.run`（`DORM_GOVERN`）手动补一次，`dorm.ext.status` 看各任务最近一次结果。所有扫描/生成都设计成幂等（`dorm_absence_warnings` UNIQUE(student,scan_date)、`dorm_hygiene_tasks` UNIQUE(room,plan_date,task_type)、出账前先 `billExists`），所以重复触发安全。

## 八、明显弱点 / 可疑之处

**1. `DormRepairStatus` 枚举与数据库不一致（最容易被追问）**
`vcampus-common/.../dto/dorm/DormRepairStatus.java` 只有 `SUBMITTED, ACCEPTED, IN_PROGRESS, COMPLETED, CANCELLED` —— **缺 V8 加的 `PENDING_REVIEW`**。整条工单链路（`RepairWorkOrderDto.status`、SQL、UI）都用裸 `String`，所以运行时不报错，但这个枚举已经不是状态的权威来源；任何按它 `valueOf` 的新代码碰到待审核工单就会 `IllegalArgumentException`。同样地 `DormGovernanceService.allowed(old, next)` 那张主模块转移表仍是旧四态，允许 `IN_PROGRESS → COMPLETED` **绕过宿管审核**，与 ext 那条 `finish → PENDING_REVIEW → review` 的流程并存 —— 同一实体有两套状态机，而 `dorm.repair.update` 对宿管是开放的。

**2. `InMemory*` 与 `MySql*` 实现语义不等价，测试通过不代表生产正确**
`InMemoryDormExtRepository` 里：`createBill(c, reading, amount, due, actor)` 直接转 `meter.createBill(reading)`，**丢掉 amount / due / actor**；`createAllocation(c, bill, student, amount)` 转 `meter.allocation(bill, amount)`，**丢掉 student**。于是「分摊落到了正确的人头上」「到期日算对了」「记账人记录了」这三件事在内存实现里根本没存，单测也就无法覆盖，只有可选且默认跳过的 `MySqlDormExtIntegrationTest` 才真正碰 MySQL。此外内存实现靠整个仓储对象 `synchronized`，而 MySQL 侧靠行锁 + 条件 UPDATE —— 并发行为完全不同，`DormLeaveService.serialized()` 也为此分了两条路径（`transactions == null` 时 `synchronized(repository)`）。

**3. 错误信息把数据库原话回传到客户端**
`DormServiceSupport.message(Exception)` 会把最内层 `SQLException.getMessage()` 截 160 字拼进用户可见的 `userMessage`：「数据库拒绝了这次操作：…（若提示某条 CHECK 约束，多半是 …还没跑）」。对答辩演示很友好，但这是把表名、列名、约束名泄露给任意已登录客户端 —— 信息泄露面，生产上应只记日志。

**4. 权限粒度有两处偏松**
① `DormExtCommandHandler.requiredPermission()` 的**默认分支是 `return Permission.DORM_GOVERN`** —— 新加一条 ext 命令若忘了登记，会静默落到宿管权限而不是被拒，是「fail-open 到某个真实权限」的写法。
② 主模块有 10 条命令 `requiredPermission()` 返回 `null`（`building.list`、`access.list`、`alert.list`、`repair.list`、`request.list`…），路由层只查「是否登录」，数据范围完全依赖服务层那句 `session.allows(DORM_GOVERN) ? 客户端传的id : 自己`。逻辑本身是对的，但保护同一件事的判定分散在两层、由不同的人各写一遍，漏一处就是横向越权。

**5. 事务边界与外部扣款混在一个事务里；跨事务读没有可重复保证**
`MySqlDormBillingRepository.pay` 与 `MySqlDormPaymentAdapter.charge` 共用同一个 `Connection` —— 好处是原子，但这意味着账户行锁（`SELECT ... FOR UPDATE`）会被持有到宿舍那两条 UPDATE 做完；`dorm.ext.bill.generate` 更极端：**整个批量出账（可能上百个房间、创建账单 + N 条分摊 + 回填读数）全在一个事务里**，锁持有时间长、失败则全部回滚，没有分批提交。另外 `TransactionManager` 用连接默认隔离级别，`DormExtWarningService.scan` 在一个事务里先读配置再逐人查请假再写预警，没有显式设 `REPEATABLE READ`。

**6. 几处性能/规模问题**
`DormExtAccessService.resolve()` 对每一行在线学生**逐行调 `repository.hasApprovedLeave(...)`**，典型 N+1；`stays()` 还把结果一次性全返回并包成 `new DormPage<>(1, max(size,1), size, rows)` —— **假分页**，全校在住学生规模下会直接撑爆一条响应（而 `SafeObjectInputStream` 的 8MB 累计预算就摆在那里）。`DormExtWarningService.scan` 同样是「拿全量 residents 逐人循环 + 逐人查请假」。

**7. 「通知辅导员」实际上只是生成一段文字**
`TASK_WARNING_NOTIFY` 这个每日 08:10 的 job 调 `pendingSevereWarnings(today)` 后只用 `warningSummary()` 拼一句「待通知严重未归 N 条：…」写进调度台账和日志，**没有任何真实投递**（无邮件、无站内消息）。而 `warning.notify` 命令写 `handle_status='NOTIFIED'` + `notified_teacher_id` 也只是记账。答辩时最好主动说明这是「留了接口、未接通道」，而不是等老师发现。
